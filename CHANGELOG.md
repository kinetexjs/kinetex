# Changelog

All notable changes to kinetex will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [1.4.0] - 2026-09-27

Connection pooling made configurable, six new capabilities, and one hundred and ninety-four defects the new tests found — four of which could take a host process down, and one of which made `Retry-After` a no-op.

### Added

- **`sessionPool` client config.** `NodeHTTP2Transport` has always accepted `sessionTTLMs`, `pingIntervalMs`, `maxSessions`, `connectTimeoutMs` and `requestTimeoutMs`, and `createTransport` has always accepted them as its third argument — but `Kinetex` passed `undefined` there, so none of it was reachable from `kinetex({ ... })`. A new `sessionPool` option (typed by the exported `SessionPoolConfig`) is now threaded through to the transport the client builds for itself.
- **`http1KeepAlive` / `http1MaxSockets`.** The legacy `node:https` path now uses a dedicated, bounded keep-alive agent instead of inheriting `https.globalAgent`.
- **Concurrency limiter (bulkhead).** `concurrencyLimit` bounds requests _in flight_, which `rateLimit` cannot: a token bucket releases at dispatch, so `rateLimit: { limit: 100 }` still permits 100 simultaneous sockets. A permit is held for the whole logical request — retries included — and handed directly to the longest-waiting caller on release, so the limit is never transiently exceeded. Queueing, a bounded queue, abort-while-queued, and `destroy()` draining are supported, plus the standalone `ConcurrencyLimiter`, `CONCURRENCY_DEFAULTS`, `ConcurrencyLimitConfig` and `ConcurrencyLimitError` (`code: "ECONCURRENCY"`). It is a field on `Kinetex` rather than an interceptor, because an interceptor wraps the dispatch and cannot gate the downstream call.
- **HTTP(S) CONNECT proxy.** `proxy` now works on Node instead of failing fast. `src/proxy.ts` dials the proxy and performs a `CONNECT` handshake for both `http` and `https` proxy URLs, with optional Basic `Proxy-Authorization`, TLS-to-target wrapping, a 64 KiB response-head cap, dial/handshake timeouts and abort support. Both built-in transports are proxy-aware: `NodeHTTP2Transport` opens the tunnel before `http2.connect`, and the legacy path hands the tunneled socket to its keep-alive agent. Failures use the existing `EPROXY` code. SOCKS5 URLs still throw, pointing at `kinetex/socks5`.
- **`dispatcher` passthrough.** An `undici` `Agent` / `ProxyAgent` / `MockAgent` is forwarded to `fetch` as `init.dispatcher` — and omitted from the init object entirely when unset, so it never overrides a globally-installed dispatcher. Node only; like a custom `fetch` it forces `FetchTransport`, since `NodeHTTP2Transport` drives `node:http2` directly and has nowhere to put one.
- **zstd decompression.** `content-encoding: zstd` is decoded through the first mechanism the runtime offers: `DecompressionStream("zstd")` (Bun, newer edge runtimes), then `node:zlib`'s `createZstdDecompress` (Node 22+), then a passthrough. Cloudflare and several CDNs advertise zstd, so this is the difference between a parsed body and a parse error. On Node 18–21 the failure names the version rather than surfacing an opaque "not a function".
- **OpenTelemetry metrics.** `OTelTracer` gains optional `recordHistogram` and `incrementCounter` methods. When present, kinetex records `http.client.request.duration` (histogram, seconds), `http.client.request.count` and `http.client.error.count`, with `http.request.method`, `server.address`, `http.response.status_code` and `error.type` attributes, following the OTel HTTP client semantic conventions. Duration covers the whole logical request including retries; errors are recorded from a `finally`; any exception a metrics backend throws is swallowed.
- **Idempotency-Key.** `generateIdempotencyKey()` (RFC 9562 v4 UUID from the runtime CSPRNG), `isValidIdempotencyKey()` and a fluent `.idempotencyKey(value?)`. The key is set on the request headers, so every retry reuses it — a fresh key per attempt would be worse than none. Validation is 1–255 visible ASCII, so CR/LF/NUL cannot be smuggled into the headers, and a runtime with no `crypto.getRandomValues` throws rather than falling back to a guessable value.

### Fixed

- **`waitForOpen` leaked every waiter it timed out (high).** The timeout callback searched for its own entry with `_openWaiters.findIndex((w) => w.resolve === resolve)`, but the resolver on the queue is a _wrapper_ — the one that clears the timer — not the promise's own `resolve`. The two are never the same function, so the search never matched, `i` was always `-1`, and the waiter was never spliced out. A timed-out caller got its `WSConnectTimeoutError` and left a dead entry behind that nothing would ever remove: a client whose `waitForOpen` timed out repeatedly grew `_openWaiters` without bound, and every subsequent `open()` and `close()` walked the corpses, calling `resolve` and `reject` on already-settled promises. The waiter is now held in a local and removed by identity, which is what the search was always trying to do. Reverting the fix makes the new suite fail on the queue length, so the assertion is the length and not the rejection — the rejection was already correct.
- **An already-aborted signal was ignored whenever a permit happened to be free (high).** The `signal.aborted` test sat inside the enqueue path, so the fast path above it — taken by essentially every real request — never looked at the signal at all. A caller whose `AbortSignal` had already fired was handed a permit and a resolved promise, and the request went out. The check's own comment said "Already aborted: never enqueue, so no permit can leak", so the intent was unambiguous and the placement was the whole defect. Every already-aborted test in the suite saturated the limiter first, so the one path a real request takes was the one path nothing exercised. The check is now first, before a permit is taken.
- **The same call reported a cancellation as a queue overflow.** With the check confined to the enqueue path, the two capacity rejections in front of it answered first: a saturated limiter with `queue: false`, or with the queue full, refused an aborted acquire with `ECONCURRENCY` rather than `EABORT`. That inverts the contract the fix above exists to establish — a caller branching on `err.code === "EABORT"` fell through to its generic branch, and a policy that retries on `ECONCURRENCY` retried a request the caller had already cancelled. One call, three answers: `EABORT` when saturated and queueing on, `ECONCURRENCY` when queueing was off or the queue full, and a resolved promise when a permit was free. All three paths now answer `EABORT`.
- **`maxQueue: NaN` made the queue cap fail open.** The cap is tested as `waiters.length >= maxQueue`, and every comparison with `NaN` is false, so a non-finite `maxQueue` stopped bounding anything: each request then parked a waiter holding its promise, signal and closures, and nothing was ever rejected. A negative value failed the other way — the first overflow was refused, so a configured depth of `-1` silently meant 0. `maxConcurrent` was validated at construction and this was not, in the same constructor, for the same reason. `maxQueue` must now be a non-negative integer or `Infinity` (the documented unbounded queue), and anything else throws a `RangeError` naming the field and the value.
- **`ConcurrencyLimiter`, `CONCURRENCY_DEFAULTS` and `ConcurrencyLimitError` were unreachable from the package root (high).** The release added them and the changelog listed them as exports, but `src/mod.ts` forwarded only `createRateLimitInterceptor` and `RateLimitError` from that module — so the limiter's own error class, named in the docs as the thing to catch for `ECONCURRENCY`, could not be imported at all except by deep import. The three values and the `ConcurrencyLimitConfig` type are now exported from the root, where the sibling rate limiter's already were.
- **`docs-drift` let a near-miss property name through.** `DRIFT_CODES` listed TS2339 but not TS2551, and TypeScript splits "property does not exist" in two: the suggestion-free form is 2339, and the near-miss form is 2551 ("Property 'x' does not exist on type 'T'. Did you mean 'y'?"). The second is the more likely one in practice, because a documented name drifts _towards_ a real one — `inFlightTypo` for `inFlight`. Config samples were saved by TS2353 firing on the surrounding object literal, so the hole only opened for samples that read a property off a typed value, which the README had not had until the concurrency section documented `limiter.inFlight`. 2551 is now treated as drift, and both shapes are verified to fail the suite.
- **An unfollowed 3xx reported `redirected: true`.** With `followRedirects: false` — or `maxRedirects: 0` — the manual follower hands the response straight back, and the line that does so set `redirected: true` on the way out. It is the one value the field must never take: no hop was taken, `res.url` is still the URL the caller asked for, and the whole point of the option is that the caller now has to read `Location` and decide for themselves. A caller branching on `if (res.redirected)` to detect a cross-origin bounce was told it had been redirected somewhere it never requested. A chain that _was_ followed still reports `true`, and both directions are now pinned.
- **A redirect failure was raised as a network error, so the whole chain was replayed (high).** `RedirectError` is exported from the public entry point, listed in the README's error-code table, and given its own non-retryable case in `shouldRetry` — and nothing in the library ever constructed it. "Too many redirects" and "Redirect loop detected" were plain `KinetexError`s with code `ENETWORK`, so they fell into `shouldRetry`'s network-error branch and were retried like a dropped connection. A chain is a deterministic answer: the same request produces the same chain. `maxRedirects: 3` put **sixteen** requests against a server already looping, and the error the caller asked for only arrived after the entire backoff schedule had been served. Both now throw `RedirectError`, so the exported error class is real, the documented code is reachable, and the cap is a cap.
- **`onAfterRequest` was declared, documented, and never invoked.** The hook appears in `LifecycleHooks` as "After the request is sent (before response is processed)" and twice in the README with example code, and nothing in `src/` called it — on any path, for any status, success or failure. A caller who registered it got silence, and the `mod` suite's own test for it set a `hookCalled` flag that was never read. It now fires in the one window it describes: after the transport answers, before the response is built, and deliberately not on the path where the transport threw, since the request was then never sent.
- **A HAR entry never recorded the request body (high).** `HAREntry.request.postData` is declared — "Posted data, if applicable" — and was never written, so every recorded POST, PUT or PATCH reached a HAR viewer with an empty request body while the response body, query string, headers and URL were all faithfully captured. It is now recorded under the gates the response side already used: a content type that is safe to record, truncated to the same limit, and a body that cannot be read without consuming it (a stream, a `FormData`) omitted rather than guessed at — which is what the neighbouring `bodySize: -1` already admitted.
- **`tests/mod.test.mts` reported success after any number of failures.** The suite closes with `process.exit(process.exitCode ?? 0)`, on the theory that node:test has already recorded the run's verdict in `process.exitCode`. It has not, and does not: when a test file is executed directly rather than through `node --test`, that property is never assigned — measured at 1.5 s and again at 4 s after the run it was still `undefined`. The forced exit is genuinely required (the suite leaks keep-alive sockets and would otherwise hang indefinitely), so the expression evaluated to `process.exit(0)`: all of its assertions were printed to the terminal and enforced against nothing, and a CI job, a `&&` chain or a mutation harness saw green. The verdict is now counted from the assertions themselves and turned into the exit status. This was found by the mutation harness, which reported five surviving mutants that had in fact each killed a named test.

- **A caller-supplied HTTP/2 pseudo-header overrode the transport's own request line (security, high).** `_sendHTTP2` built its header block as `{ ":method", ":path", ":scheme", ":authority", ...currentReq.headers }`, so a request handed straight to `transport.send()` — the documented use of both built-in transports — could carry its own `:path` and `:authority`, and the transport would dial them. The URL that `isSafeURL` screens is not the URL that got dialled. The validation loop could not catch it either, because it skipped every name beginning with `":"`: `strict: true` returned a clean 200 for a hijacked `:path`, and `FetchTransport` dropped the very same header, because `":"` is not a token character. One request, two transports, two answers. The transport now owns the request line — a caller pseudo-header is refused, reported through `onDroppedHeader` or a warning, and raised as `EVALIDATION` in strict mode before anything is dialled.
- **A `__proto__` header vanished silently on the raw Node paths.** `__proto__` is made of token characters, so it is a legal header name and passes `isValidHeaderName`. The HTTP/2 header block was populated with `h2ReqHeaders[name] = value`, a `[[Set]]` that hit the inherited `__proto__` setter — which ignores a primitive. The header did not overwrite anything: it disappeared, and neither `onDroppedHeader` nor `console.warn` said so, against a contract stated in the code that a header is never dropped silently. It is now written as a data property, which is what `FetchTransport` already did, so the two transports finally agree on whether it is sent.
- **The redactor skipped field redaction for every `+json` body.** The gate that decides whether a body is logged at all is `allowedBodyTypes`, matched with `startsWith`; the gate that decided whether its configured `bodyFields` were then redacted was a much narrower `contentType.includes("application/json")`. Any configuration wide enough to admit a structured-suffix body — `allowedBodyTypes: ["application/"]` is the natural one — therefore logged `password` fields in the clear for `application/vnd.api+json`, `application/hal+json` and every other `+json` type, which is the family GitHub, HAL and RFC 7807 all use. The media-type test is now at least as wide as the gate above it: `application/json`, any `+json` suffix, `text/json`, case-insensitively and ignoring parameters, matching what this library already parses as JSON elsewhere.
- **`CookieJar.fromJSON` could produce a jar whose cookies were never sent.** `fromJSON` is the one public ingestion path that takes externally authored JSON, and it copied `sameSite` through verbatim. `SameSite` is a closed union — `"Strict" | "Lax" | "Unset" | "None"` — and `sameSiteAllows` switches on it, returning `undefined` for anything else; `getCookies` filters on that result. A persisted `"lax"`, a value from a non-JS writer, or simply an omitted field, therefore produced a jar whose `count` was 1 and whose cookie was not sent to anything, with no error anywhere. The value is now canonicalised on the way in, and anything unrecognised becomes `"Unset"` — the documented "cannot tell" bucket, which still refuses an explicit cross-site request, so the fail-closed half of the contract is unchanged.
- **`maxRequestSize` approved multipart bodies larger than the limit it had just checked.** The `FormData` branch of the size guard estimated the payload with a flat 76 bytes per part, described in a comment as conservative. It is not: `encodeMultipart` writes `--` plus a 70-character generated boundary plus `Content-Disposition` framing, so the real cost is roughly 45 bytes per part more than the guess. A two-field form measured 234 bytes and went out as 323 with a limit of 234, and a five-field form measured 471 and went out as 692. The limit was a lie for exactly the body type the guard had been added to cover. There is now no estimate: the body is encoded once — the same call the dispatch path needs anyway, so it is not encoded twice — and its real byte length is what gets compared.

- **`mergeSignals` threw away the reason a request was aborted.** When any input signal was already aborted, the function built a fresh controller and called `controller.abort()` with no argument, installing the platform's generic `AbortError: This operation was aborted` and discarding _why_. The two-live-signal branch preserved the reason, and so does the `AbortSignal.any` implementation this function prefers on every current runtime — so the one case a caller is most likely to hit was the only one that lost it. The loss propagated: the timeout interceptor re-aborts with `existing.reason` when it merges, so a caller's `AbortSignal.timeout()` — or their own `RangeError("quota exhausted")` — arrived downstream as a bare abort with nothing left to tell a timeout from a manual cancel. The original signal's `reason` is now carried through, and a pre-aborted merge reports exactly what `AbortSignal.any` would.
- **`imdsCredentials` let a non-JSON body escape as a raw `SyntaxError`.** Every other failure in the function is a `NetworkError` with a `code`, but `Response.json()` was called unguarded: a proxy's HTML 502 page surfaced as `SyntaxError: Unexpected token '<'` with no `code` at all, so a caller branching on `err.code === "ENETWORK"` never saw it, and the message named no part of the request. The parse is now wrapped like the rest of the function.
- **`imdsCredentials` accepted a body with no usable fields as valid credentials (high).** The response was cast to a credential shape and its fields read without validation, so `{}` produced `accessKeyId: undefined` and `{"AccessKeyId": null, …}` produced nulls — both returned as a _successful_ result. Those went on to produce a SigV4 signature AWS rejects as `SignatureDoesNotMatch`, an error that points at the caller's code rather than at the metadata endpoint that had actually answered with nonsense. All three required fields are now validated as non-empty strings and every missing one is named in a single `NetworkError`.
- **`normalizeHeaders` kept only the last `Set-Cookie` (high).** `Set-Cookie` is the one header the Fetch spec does _not_ combine: `Headers.forEach` yields each cookie as a separate entry, while every other repeated header arrives already joined with `", "`. The loop assigned, so the second cookie overwrote the first and it vanished with no error anywhere. A response setting `Set-Cookie: a=1` and `Set-Cookie: b=2` normalized to `"b=2"` — and the two cases that make it worse are the common ones: any login that establishes a session cookie alongside a CSRF or preference cookie silently lost the first. `FetchTransport` normalizes every response through this, so the loss reached the cookie jar on any runtime where the fetch transport is used (browsers, Deno, Bun, and Node whenever `dispatcher` or a custom `fetch` is set, or `httpVersion: "HTTP/1.1"`). Values are now accumulated into the same combined form `Headers.get("set-cookie")` reports, which `splitSetCookieHeaders` splits back apart — including the `Expires=Wed, 09 Jun 2021 …` case where the cookie itself contains a comma. `toNodeHeaders` and the `HttpHeaders` constructor were already correct and are unchanged.
- **Redirect safety gates were unreachable for ordinary requests (security, high).** `_sendFollowingRedirects` is the only place kinetex inspects a redirect _target_: the SSRF screen (`isSafeURL` per hop), the `httpsOnly` policy, the loop detector, the `maxRedirects` cap, the RFC 7231 method downgrade, and the capture of intermediate `Set-Cookie` and the stripping of cross-origin credentials. It was entered only when a cookie jar or a forwarded credential header happened to be configured — and a plain `GET` is neither. So a plain GET's redirects were chased by the transport instead and every one of those checks was skipped: the HTTP/2 loop resolved any `Location` and dialled it, and `FetchTransport` handed fetch `redirect: "follow"`, which does the same. A 302 to `http://127.0.0.1:9/` opened the socket (`ECONNREFUSED` came back _from the loopback port_, which is the point — nothing refused it first) and a 302 to `http://169.254.169.254/` was answered by the cloud metadata service with a 401 that surfaced to the caller as an ordinary `EHTTPSTATUS`. `httpsOnly: true` changed nothing on either path; both reported the same opaque `ENETWORK "Protocol error"`. Redirects are now always followed by hand, so every hop is screened regardless of how the request was configured.
- **The HTTP/2 transport's own redirect loop checked nothing about the target (security, high).** Even with the client fixed, that loop is the only follower for any direct use of `NodeHTTP2Transport`, and it resolved the `Location` and dialled it with no protocol gate and no `isSafeURL` screen. A cleartext target failed only by accident — the transport hardcodes `:scheme: "https"`, so the hop died as `ERR_HTTP2_ERROR: Protocol error` — which meant a downgrade was impossible without being _refused_, and an `httpsOnly` client could not tell the difference. Both gates now throw `EVALIDATION`, with any userinfo in the target redacted.
- **`noCache()` was a no-op.** `CacheRequestConfig.forceRefresh` was declared in `src/types.ts` and read nowhere in the codebase. `noCache()` set it, and the cache lookup then ran exactly as if no option had been passed, so a warm entry was served and the fluent method documented as "Force a fresh fetch, bypassing any cached response" did not fetch. The lookup now skips the read for that request; the write still happens, which is what "refresh" means, so a later plain request is cached again.
- **`FormData` bodies reached the raw Node transports as zero bytes (high).** `serializeRawBody` exists precisely so the fetch-bypassing transports do not send an empty body for a type fetch would have serialized, and it covered `URLSearchParams` and `Blob` — but not `FormData`. On `NodeHTTP2Transport`, Node's default, a form upload went out with no body and no `Content-Type` at all; the server recorded `form: {}` and answered 200, so nothing downstream could tell. The new exported `encodeMultipart()` builds the RFC 7578 bytes, and the client encodes the form before dispatch so the body and the `content-type` boundary header are produced together. A field name containing CR, LF or a quote is refused with `EVALIDATION` rather than used to forge part headers. Encoding happens _before_ the header block is built on both raw Node paths, because the boundary is generated during encoding: the first version of this fix encoded the body inside the stream writer, after `session.request()` had already been handed its headers, so the body carried a boundary no header named.
- **`splitSetCookieHeaders` truncated every cookie carrying an `Expires` (high).** Splitting a collapsed `Set-Cookie` header is non-trivial for exactly one reason, and the function's own doc comment names it: `Expires` values contain a comma. The split condition was "have we seen a value or an attribute yet", which is true the instant the first `=` is read, so it committed on _every_ comma. `sid=xyz; Expires=Wed, 09 Jun 2021 10:18:14 GMT; Path=/; HttpOnly` came back as two fragments, the first of them `sid=xyz; Expires=Wed` — the cookie silently losing its expiry — and a legitimate two-cookie header was shredded into pieces like `09 Jun 2021 10:18:14 GMT; Path=/; HttpOnly`. `HTTPCookieJar` reads responses through this path, so the truncation reached the cookie store, not just the exported helper. A comma now separates cookies only when the text up to the next `,` or `;` opens a `name=` pair. Not one of the file's 146 tests used an `Expires` value.
- **`domainMatch` returned `false` for a cookie domain with a leading dot.** RFC 6265 §5.2.3 says a leading `%x2E` is ignored, and this function's own JSDoc gives `".example.com"` as its example argument — for which it answered `false`, as it did for the host itself and for every subdomain of it. The common `Domain=.example.com` spelling matched nothing. `parseSetCookieHeader` happens to strip the dot, which is why the cookie jar was unaffected and the bug survived.
- **`getRegistrableDomain` returned a fragment for a fully-qualified host.** `getPublicSuffix` strips a trailing FQDN dot; this function did not, so the two disagreed about the same input and the result was the rightmost labels of the _unstripped_ string: `www.example.com.` → `m.`, `1.2.3.4.` → `4.`. A caller validating a cookie domain against that is comparing against a non-domain.
- **IPv6 detection was both too loose and too strict.** The test was `/^[\da-f:]+$/` plus "contains a colon", which accepted `abc:123` and `cafe:babe` — hostnames spelled entirely in hex characters — and rejected the IPv4-mapped forms `::ffff:1.2.3.4` and `::1.2.3.4`, which are real addresses, for which `getRegistrableDomain` then returned the fragment `3.4`. The check is now structural: at most one `::`, a compressed form standing for at least one omitted group, an unadorned form needing all eight, and a dotted-quad tail folded into the two hextets it occupies.
- **A cookie value wrapped in control characters was silently trimmed instead of rejected.** `parseSetCookieHeader` trimmed the value before validating it, so a CTL at either end was removed along with the surrounding space and the check never saw it — `a=\r\nX-Injected: 1` parsed as the cookie `a` with the value `X-Injected: 1`. An interior control character was already refused, so the rejection applied only from the second character in. The value is validated first and trimmed after; the documented leniency (spaces, tabs and commas are data) is unchanged.

- **A window smaller than the threshold silently disabled the circuit breaker.** The window is a sliding buffer of the most recent `windowSize` results, so it can hold at most `windowSize` failures. With `windowSize` below `failureThreshold` the test `failures >= failureThreshold` is unreachable and the circuit can never open: `{ windowSize: 2, failureThreshold: 5 }` stayed `CLOSED` through 50 consecutive failures, with no error, no warning and no other symptom — a breaker that appears configured and does nothing. The window is now widened to the threshold (the smallest coherent reading of the configuration) and a `console.warn` names both values. `windowSize: 0`, the documented consecutive-count mode, is left alone. Two tests in `tests/circuit-breaker.test.mts` and one in `tests/regressions.test.mts` were written around the broken configuration and have been rebuilt on reachable ones.
- **`state` and `snapshot` went stale once the reset window elapsed.** The OPEN → HALF_OPEN transition was time-based but only ever evaluated inside `execute()`. A health endpoint or dashboard polling `breaker.state` therefore saw a stale `OPEN` for as long as no request arrived, and could not distinguish a circuit that was about to probe from one that had been down for an hour. Both reads now apply the elapsed-time check. The read is pure: `onHalfOpen` still fires from `execute()`, so observing the state never mutates the breaker.
- **A half-open rejection reported `Circuit breaker OPEN`.** The half-open probe limit rejects callers too, and in that case the state snapshot says `HALF_OPEN` — the circuit is recovering, not open. The message said `OPEN` regardless, pointing operators at the wrong problem during exactly the window they were watching to see recovery. The message now reports the state the snapshot reports.

- **`resetStats()` zeroed the cache's capacity gauges, and eviction then ran on a fiction (high).** `totalEntries` and `totalSizeBytes` are not counters — they describe what is actually stored — but the reset cleared them along with `hits`/`misses`/`evictions`, and `_ensureCapacity()` reads them as the authoritative figures for the `maxEntries` and `maxSizeBytes` caps. After one `resetStats()` the guards read as if the cache were empty, so a `maxSizeBytes: 600` cache was measured holding **1028 bytes across 4 entries** where 2 fit, and nothing evicted them. A monitoring call on a scrape interval silently removed the memory bound. The reset now touches only the counters; the entry count and byte total survive, and `getStats().totalEntries` no longer reports `0` for entries that are still there and still being served. Use `clear()` to empty the cache.
- **`max-age=0, stale-while-revalidate=N` was never cached.** `computeTTL` computed the SWR window and reported `shouldCache: true` on the strength of it, and the very next guard in `set()` discarded that decision because the freshness lifetime was zero. This is the canonical CDN recipe — serve the stale copy immediately while one request revalidates in the background — and it silently did not work. `stale-if-error` was broken the same way, one guard earlier: `shouldCache` did not consider that window at all. A zero lifetime is now storable whenever either window covers it, and a zero lifetime with no window is still refused.
- **A `Last-Modified` in the future produced a negative freshness lifetime.** RFC 9111 §4.2.2 derives the heuristic as 10% of the interval between `Last-Modified` and the response's `Date`. When the origin's clock runs ahead of the client's — routine, and the same skew this library corrects for in AWS signing — that interval is negative, and there was no lower clamp, so the entry was stored with an `expiresAt` and a `staleUntil` _before_ its `createdAt` and no window could ever cover it. The clamp to `0` is the RFC's "already stale"; the stale windows then apply normally instead of landing in the past. Past `Last-Modified` values are unaffected.

- **`maxDelayMs` was not a maximum.** The cap was applied to the exponential base and jitter was then added on top, uncapped, so the returned delay exceeded the documented ceiling by up to `base * jitter`. With `baseDelayMs: 1000`, `maxDelayMs: 1200` and `jitter: 1` the client waited 2000 ms; with the default 0.3 jitter a 30 s cap permitted 39 s. The option exists to bound worst-case latency and it did not. The cap is now re-applied after jitter.
- **`Cache-Control: no-cache` was served as a fresh hit forever.** RFC 9111 §5.2.2.4 allows such a response to be _stored_ but forbids reusing it without revalidating. kinetex stored it and then reported it as an ordinary fresh hit with nothing recorded, so an origin that asked to be consulted again was ignored and its body served indefinitely from cache. The directive is now recorded on the entry and such entries are reported as stale, which routes them into the existing serve-stale-and-revalidate path. `no-store` and `max-age=0` were already refused outright and still are.
- **Retry jitter was dead code as far as the suite was concerned.** Every retry test pinned `jitter: 0` for determinism, so `base + base * jitter * random()` was never evaluated against a non-zero jitter: deleting the term entirely passed all 3,647 tests. The five new tests seed `Math.random` and pin the arithmetic at five seeds, at the default 0.3, at 1.0, against the `maxDelayMs` ceiling, and against a server `Retry-After` (which must not be jittered at all).

- **`Retry-After` and clock skew: the AWS signing correction was inert.** `SigV4Signer` shipped with `updateClockSkew`/`handleClockSkewError` and `detectClockSkew` is a public export, but nothing in the library ever called them. A client with a wrong clock got a 403 `RequestTimeTooSkewed`, and — because 403 is not in the default `retry.statuses` — simply failed. The signer is now kept on the client and consulted on a status error: a recognised skew error updates the signer's clock and buys exactly one retry, which re-signs with the corrected date. The correction is bounded to one attempt per logical request, so a server that keeps reporting a different time cannot spin, and a 403 that is not a skew error is left alone.
- **`detectClockSkew` read only the `Date` header.** `x-amz-date` is AWS's own signed timestamp and is present on the clock-skew error itself; `Date` is written by whatever proxy fronts the endpoint and is frequently absent. Reading only `Date` made the skew silently undetectable on exactly the responses that carry it — and when both were present, a stale `Date` won over the authoritative one. `x-amz-date` is now preferred, and parsed from AWS's basic ISO 8601 form (`20300101T120000Z`), which `Date` cannot parse at all. Out-of-range components (`20351301…`, `20350132…`, `20350101T250000Z`) are rejected rather than rolled over into a plausible wrong instant.
- **The `awsSigning` skew test asserted nothing.** `SigV4Signer.updateClockSkew updates skew` called the method with an `x-amz-date` header and no assertion at all — which is exactly how the gap above survived. Both skew tests now pin the computed value against the expected epoch and assert the corrected skew changes the signed date.

- **An explicit `Host` header was merged with the URL host, producing a signature that could never validate.** Setting `Host` yourself is how you sign for a virtual-hosted-style bucket, a custom endpoint or a proxy, and both `sign()` and `presign()` supported it. The URL host was nevertheless injected unconditionally, so a caller header in any casing other than lowercase survived alongside it; `buildCanonicalHeaders` lowercased both and its dedupe step joined the values, so the request was signed as `host:override.example,s3.amazonaws.com` with a duplicate entry in `SignedHeaders`. AWS rejects that with an opaque `SignatureDoesNotMatch`. An explicit host, in any casing, now wins.
- **An empty header name reached the canonical request.** `""` is not a valid HTTP field-name (RFC 9110 §5.1), but it was canonicalized like any other: the request carried a `:value` line and a leading `;` in `SignedHeaders`, neither of which the signature can ever validate. Empty names are now dropped. Real headers alongside an empty one are still signed.
- **`presign()` warned about an out-of-range `expiresIn` and then used it anyway.** `X-Amz-Expires` is validated by AWS, not by kinetex: `0` and negative values produce a link that has already expired when it is fetched, a fractional value is not a valid integer, and anything past the ceiling is refused outright — an S3 link asking for 700000 s fails with `AuthorizationQueryParametersError`, and a non-S3 service caps at one hour. All of these were emitted verbatim behind a `console.warn`, and the warning repeated only the rejected input, never the value actually applied. The value is now floored and clamped to `[1, 604800]` for S3 and `[1, 3600]` elsewhere, and the warning names the clamped result. Two existing tests asserted the old out-of-range output and were themselves pinning the defect.

- **A new cookie could be orphaned by the very eviction it triggered (high).** `putCookie` created the `(domain → path → name)` maps for an incoming cookie and _then_ called `evictForDomain()`, which prunes empty path maps as part of its own bookkeeping — so the prune deleted the map that was about to be written into. The cookie landed in an orphaned map that nothing could reach: `setCookie()` returned `true`, the cookie was never sent, and `getAll()`/`toJSON()` could not see it. `this.total` was incremented regardless, so the counter climbed while the jar emptied — measured at **`count === 5` with 2 cookies stored** — and because `evictGlobal()` reads `this.total`, the global cap stopped bounding anything either. Eviction now runs before the maps exist, and the maps are re-fetched afterwards in case eviction dropped the domain entirely. A cookie set at a new path while the per-domain cap is full is now actually stored and actually sent.
- **`getCookies()` returned the stored objects themselves, not copies.** `jar.getCookies(opts)[0].value = "x"` rewrote the jar's contents, while `getAll()` and `getForDomain()` — the two methods sitting directly beside it — both return copies, leaving the same API disagreeing about whether the result was yours to modify. Every accessor now returns copies.
- **A `getCookies()` snapshot reported the access it had just performed.** The last-access stamp is what LRU eviction orders by, so it is written to the _stored_ cookie; taking the copy afterwards meant the object handed to the caller was already stamped with the read that call itself performed, and a later mutation of that object could write the timestamp back into the store. The snapshot is now taken first and the stamp applied after: a caller sees the cookie as it was at the moment of the call, the jar records the access, and the two can no longer interfere.
- **A rehydrated jar could send a cookie scoped to a public suffix (security).** RFC 6265 §5.3 requires that a cookie's domain not be a public suffix, and `setCookie()` enforces it. `fromJSON()` / `loadCookieJar()` write straight into the storage map and skip `setCookie()` entirely, so a persisted cookie with `domain: "com"` — which `setCookie` refuses — was attached to every `.com` request. Anyone able to write the serialized jar (an XSS bug plus `localStorage`) had a cross-site cookie-tossing primitive against a jar that was supposed to be self-defending. Retrieval re-validates the rule for rehydrated entries, as it already did for the `__Secure-` / `__Host-` prefixes on the same path.
- **`getCookiesForDomain()` disagreed with the `Cookie` header it claims to describe.** The method documents itself as returning "cookies that would be sent to this domain", and it did not. It ignored `hostOnly`, so asking about `example.com` listed the host-only cookie belonging to `sub.example.com` — a cookie that never reaches `example.com`; it walked only _down_ the tree, so asking about `sub.example.com` missed the `Domain=example.com` cookie that genuinely applies to it (one cookie reported where the header sent two) and `deep.sub.example.com` returned nothing at all; and it applied no public-suffix rule. A domain is now in scope if it is the queried host, a subdomain of it, or an ancestor of it, with host-only and public-suffix filtering on top, and the result is pinned against `getCookieHeader()` for the same URL. It also returned the stored objects while the method directly above it returned copies, so it now copies too.
- **Overwriting a cookie left the counter above the number of cookies held.** Re-setting an existing `(domain, path, name)` slot replaces the value and keeps the original `createdAt`; it is the same slot, so `total` must not move. Nothing incremented it on that path, so the drift came only from the orphaning above — but the invariant is now asserted directly, because `count` is the number `evictGlobal()` plans against.
- **8 duplicate tests removed across `cookie-store` and `cookie`.** `tests/cookie-store.test.mts` contained eight byte-for-byte copies of tests that already existed elsewhere in the file, and one test asserted a `count` of 5 that was only reachable because of the counter drift above. They inflated the reported total and hid the fact that `maxPerDomain` had never been observed to hold.

- **A method's spelling decided whether it was deduplicated.** `methods` has always been documented — and implemented — as case-insensitive: the filter uppercases the caller's string before testing it. The dedup _key_, however, was built from the caller's spelling, so `execute("get", url)` and `execute("GET", url)` were two different keys. The one casing mistake a caller makes most often silently turned deduplication off, and `keys` reported the split. The method is canonicalised before it reaches the key function, so a custom `keyFn` now receives `GET`, not `get`.
- **A caller that opted out of the window destroyed it for everyone.** `execute(..., windowMs: 0)` means "do not reuse a result for me". The entry it found had already resolved, so that path fell through to `inflight.delete(key)` and led a new request of its own — deleting a window some _other_ caller had established and was still relying on. Measured: one such call emptied the map, and the next windowed caller went to the network for a result that was still in hand. A bypassed caller now runs its own factory and leaves the entry alone; the stale-window path, which is the caller's own to expire, is unchanged.
- **An aborted leader's timer could delete the leader that replaced it.** Aborting drops the entry so waiters fall through, and the next caller for the same URL becomes the new leader — while the old factory is still running. When the old promise settled it registered a window timer for a key it no longer owned, and when that timer fired it deleted the _new_, still-in-flight entry. The request after that started a third copy of a request already in the air. The success and failure handlers now check that the entry still owns the key before acting on it, which is exactly the invariant the "clear any previous timer" comment was reaching for and which the abort path bypassed. The failure path had the same flaw and could additionally delete a live leader, turning one request into two.
- **Bypassed calls were invisible to the metrics, so a hit-rate dashboard read a flat zero.** `misses` is documented as "requests that triggered a real network call", but both bypasses — a method outside the filter, and a signal that is already aborted — returned before the counters were touched. A client whose traffic was all `POST` reported `totalRequests: 0` and `hitRate: 0` no matter how much it sent, and `hitRate` is the only figure anyone enables a dedup map to watch. Both bypasses now count as misses.
- **`client.dedupMetrics` reported three of the six fields the map tracks.** The wrapper exposed `hits`, `misses` and `inFlightCount` and dropped `totalRequests`, `hitRate` and `trackedKeys` — so the hit rate, the reason to enable deduplication at all, was unavailable on the client even though `DedupMap.getStats()` computed it. It now returns the full snapshot, and there is one shape to read rather than two.
- **Tests hardened across `tests/dedup.test.mts`.** `getStats` was six `typeof x === "number"` checks, satisfied by any number including `NaN` and by an object of the wrong shape; the whole snapshot is now pinned to exact values, and `inFlightCount` and `trackedKeys` are distinguished rather than treated as interchangeable. `hitRate > 0` accepted 0.01 and is now pinned at `0.5`, `0.75` and `1`. Two `clear()` tests were identical except for the window length and neither checked the timeout — the part that actually leaks, since it holds the key and the result alive for the whole window. `resetMetrics` and `clear` were indistinguishable in what they asserted, and are now distinguished by the window surviving one and not the other. A test whose own comments said it checked nothing ("For the abort handler timeout clearing, we need the abort to fire during inflight / which is tested in...") is now a real assertion. `disableDedup()` was satisfied by a `dedupMetrics === null` check alone, and now proves three concurrent requests produce three distinct responses.

- **Every DOM type guard accepted the wrong built-ins.** `isHeaders` duck-typed on `forEach`, `isURLSearchParams` on `has`, `isReadableStream` on `getReader` — one method each — and each of those names is carried by one of the most common objects in the language. Measured: `isURLSearchParams(new Map())`, `isURLSearchParams(new Set())`, `isURLSearchParams(new Headers())`, `isHeaders(new Map())` and `isHeaders(new FormData())` were all `true`. A guard whose entire job is to route a value to the right code path was handing out `Map`, `Set` and `FormData`. They now test the platform brand: `instanceof` first, which is authoritative in-realm and survives subclasses, then `Symbol.toStringTag` for cross-realm values, which additionally requires the type's own methods — the brand alone is one getter away from anything, and a class that returns `"Headers"` from `Symbol.toStringTag` with no methods is now correctly refused.
- **`isBlob` rejected every `File`.** The check was `constructor?.name === "Blob"`, and `File`'s constructor is named `File` — so the value you get from a file input, the single most common Blob-shaped value in a browser, was not a Blob. `File` extends `Blob`, and `instanceof` says so.
- **`isPlainObject` accepted every class instance.** `Object.prototype.toString.call(x) === "[object Object]"` is true for any object whose class does not override `Symbol.toStringTag`, so `new (class { constructor() { this.a = 1 } })()` passed — the opposite of what "plain" means, and the reason the guard could not be trusted for the copy/merge decisions its name invites. What makes an object plain is its prototype: `Object.prototype`, or none at all, since a null-prototype object is a dictionary and still plain.
- **`mergeSignals` left a permanent `abort` listener on every input, forever (high).** The hand-rolled merge attached a listener to each input and removed it only when one of those inputs fired. The "9.11" comment claimed the merged signal cleaned up when it aborted — but the merged controller is never handed out (the return value is a bare `AbortSignal` with no `abort` method), so that listener could never run and nothing else could ever release them. `src/core.ts` calls `mergeSignals(request.signal, controller.signal)` on **every request**, so a caller who passed a long-lived signal accumulated one listener per request for the life of the program, tripping Node's `MaxListenersExceededWarning` at 11 and growing without bound. Measured: 100 merges left 100 listeners behind. `AbortSignal.any` is used where it exists (Node 20.3+, Deno, Bun, current browsers) and holds its inputs weakly; the manual path remains for Node 18, where the same lifetime caveat applies.
- **Tests hardened across `tests/utils.test.mts`.** The SSRF guard — the single most security-relevant function in the file — was tested with exactly one public URL and two private IPs. It is now pinned across every loopback spelling (`127.1`, `2130706433`, `0x7f000001`, `0177.0.0.1`, `[::1]`, `[::ffff:7f00:1]`), every reserved range, **and the first address outside each one** — a guard that blocked the whole internet would have passed the original test, and would pass a range-only one. `parseUntrustedJSON` was compared against nothing, so "it is just `safeJSONParse`" would have passed; it now shows each of its four tighter limits rejecting what the defaults accept. `safeJSONParse` never tested `maxObjectKeys`, never showed that a limit applies inside a nested value rather than only at the root, and never asserted the failure shape (a result that left `value` present would have passed). `perfNow` asserted only `> 0` — true of `Date.now()` — and now pins monotonicity, sub-millisecond resolution and wall-clock independence. `deepClone`'s Map case checked only `get("k")`, which a clone returning the _same_ Map satisfies. Four "returns a boolean" runtime tests accepted `new Boolean(false)`. **86 \u2192 93.** `isValidHeaderValue accepts valid values` listed DEL as valid and hid it with a trailing `.slice(0, 5)`, so a reader could not tell from the file whether DEL was accepted or excluded \u2014 it is now in the invalid list, in its own assertion. `ArrayBuffer input converts` checked a length, so a version that wrapped the input in a live view passed while the sibling `Uint8Array` test checked the copy. `uint8ArrayToBase64` had two tests, both under five bytes: the chunked path is most of the function \u2014 24 576 bytes per segment, each padded only at the end, with the mid-stream `=` stripped \u2014 and a chunk size that was not a multiple of 3, or a `=` stripped from the wrong side, would have passed all of it; it is now pinned against a single-pass reference at both sides of the boundary and at three non-multiple-of-3 lengths. A prior round asserted `deepClone(/a/g)` deep-equals `{}` as a documented boundary; that assertion is now split \u2014 the host-object half still holds and is pinned, and the class-instance half is the fix above. A new regression suite pins one case per fix.

- **A `filter` silently dropped and duplicated items (high).** The paginator advanced its offset by the number of items that _survived_ `filter`, rather than the number the server returned. Whenever a filter dropped anything, the next request therefore asked for rows the client had already seen and stepped over rows it had not. Measured with a parity filter over three-item pages: offsets `0, 2, 4, 6, 8, 10` instead of `0, 3, 6, 9` — the odd items were never yielded at all, and every even one was yielded twice. A `filter` is the normal way to paginate past irrelevant rows, and the corruption is invisible in the results. The offset now advances by the server's count; `transform` (which is 1:1) and an explicit `getNext` are unaffected.
- **`totalFetched` counted the items a filter _kept_, not the ones fetched.** The same page was then described two different ways by two fields of the same state: the offset advanced by `rawCount`, what the server returned — which is the whole reason it advances by `rawCount_ — while `totalFetched`added`items.length`, the count _after_ `filter`and`transform`. Measured with a parity filter over four-item pages: 8 rows requested before the second fetch, reported as `totalFetched: 2`. Any `hasNext`written against`totalFetched` under-counted the work done, so a filter dropping half of every page also halved the total, and the state handed to a resuming caller disagreed with the offset it was resuming from. It now counts what was fetched, which is what the name says; with no filter the two definitions coincide.
- **`takeItems(0)` returned one item, and so did every negative N.** The loop pushed an item and only _then_ tested `items.length >= n`, so `takeItems(0)` yielded the first row and `takeItems(-5)` did the same (`1 >= -5`). The README documents `n <= 0` as returning `[]`, so the code contradicted its own stated contract rather than leaving it undefined. A non-positive or `NaN` count is now answered with `[]` without touching the network, fractional counts floor, and `Infinity` still means "more than exists" — the documented case that must not be swallowed by the same guard.
- **`prefetchPaginate` prefetched nothing (high).** `enqueue` awaited `gen.next()` before queueing it, and the consumer loop awaited `enqueue()` before yielding the page it already had. The consumer was therefore blocked on the _next_ page's fetch before it could be handed the current one — strictly worse than a plain `paginate`, which at least never waits. The `prefetchAhead` argument, the entire purpose of the function, bought a queue and no overlap. The pending call is now queued instead of its value, so a request is in flight while the consumer works. This is overlap and not request-level parallelism: `paginate` is a single async generator and runs one body at a time, so `prefetchAhead` bounds how far the consumer may run ahead, not how many sockets are open.
- **Abandoning a `prefetchPaginate` mid-stream could take the process down.** A consumer that `break`s out of the `for await` leaves queued requests in flight with nobody awaiting them. If one of those rejects — an aborted request, an error on a page the consumer never wanted — the rejection is unhandled, which terminates a Node process outright and surfaces in a browser as a global `unhandledrejection` the caller can neither catch nor attribute. Stopping early is ordinary usage. Queued requests are now marked handled; a failure a consumer _is_ there to receive still propagates to it unchanged.
- **One failing source aborted a whole `mergePaginators`.** Merging is for fanning out across endpoints, and a single endpoint erroring ended the entire iteration and discarded everything the healthy sources had already yielded — silently, with no error to explain the short stream. The failing source is now dropped from the rotation and the others continue, which is the isolation the transports and the batch flushes already apply. When every source fails the merge simply ends, yielding nothing.
- **A `rel` of `"Next"` ended pagination one page early.** RFC 5988 §3.1 states that relation types are compared case-insensitively, and RFC 8288 §4 makes parameter _names_ case-insensitive too, but the link-value regex matched `rel` case-sensitively. A server sending `rel="Next"` — legal, and common in the wild — produced no next page: rows silently skipped, no error, no warning. Both the parameter name and the relation value are now compared case-insensitively. This is a second, independent cause of the early-stopping failure already fixed above for URLs containing a comma.
- **A paginator that could not advance looped forever.** `hasNext` and `getNext` are two independent callbacks, and nothing checked that agreeing to another page had actually given the fetcher something new to ask for. `maxPages` defaults to `0` — "unlimited" — so a disagreement had no bound at all: a Relay connection reporting `hasNextPage: true` beside a null `endCursor` was followed indefinitely, re-fetching the same page on every tick, as was a cursor API that kept handing back the cursor it was given. The only symptom is that the `for await` never returns. Iteration now stops when a cursor or token repeats a value already used, or when a cursor-driven strategy's `getNext` reports nothing new. `page`/`offset` strategies are unaffected — a null `getNext` there is a no-op, not a stop — and a real cursor chain still walks to the end.
- **`serializePaginationState` threw on a non-Latin-1 cursor.** `btoa` takes a _binary_ (Latin-1) string and throws `InvalidCharacterError` above U+00FF. A cursor is opaque and may hold any character, so `cursor: "curseur-é-☃"` made serialization fail outright and the paginator un-resumable, with an error that named nothing about the state. The transport is UTF-8 now, chunked so a large state cannot trip the `String.fromCharCode` argument limit. The ASCII encoding is byte-for-byte what it was, so state written by the previous version still reads back.
- **`deserializePaginationState` accepted any JSON as a `PaginationState`.** `atob` and `JSON.parse` succeeding says nothing about the shape. `{"hello":"world"}`, `[1,2,3]`, `"a string"`, `null` and `42` all came back typed as a `PaginationState`, so a caller resuming from one read `page`/`offset`/`done` off an object that had none and the paginator restarted from `undefined` rather than saying so. The shape is now checked, and the prototype-pollution strip that was already there still runs first.
- **`parseLinkHeaderNext` gave up on any URL containing a comma.** The header was split on every comma, and a URI is allowed to contain one — `?ids=1,2,3` is routine. The entry was cut in half, the `rel` was no longer found, and the function reported "no next page": GitHub-style pagination stopping early against a server that had more to give, with no error. - **Aborting a request queued on the concurrency limiter lost its error code.** `ConcurrencyLimiter.acquire()` documents — and every other abort path in the library implements — a rejection carrying `code: "EABORT"`, but the two abort branches rejected with a bare `new Error("Concurrency acquire aborted")`, which has no `code` and no `isAbort`. A caller following the documented contract (`if (err.code === "EABORT")`) silently fell through to its generic error branch, and an abort was indistinguishable from a queue overflow. Both branches now raise `KinetexError(…, "EABORT")`, so `err.code` and `err.isAbort` behave here as they do everywhere else. Three regression tests cover it; reverting the fix fails exactly those three.
- **`assert.ok(x === y)`-style and log-only assertions removed across the suite.** Roughly 40 tests asserted nothing verifiable: a `console.log` of a status, a `let threw = false` flag, a `try {} catch {}` around an expected rejection, or a network-skip `catch` that enclosed its own `assert.equal` and so reported a pass for a broken implementation. Each now asserts the concrete error type and code, the exact value, and — where a live API is involved — only tolerates a genuine transport failure. Tightening these is what surfaced the three defects above: the WebSocket tests had been reporting success while `client.ws()` was unusable, and the APQ tests had been reporting success against an endpoint that rejects automatic persisted queries outright, so the feature was never exercised. Both now drive a local server that actually speaks the protocol.

- **`qop=auth-int` was selected, advertised, and never actually computed.** RFC 7616 §3.4.4 explicitly allows a server to offer `qop="auth-int,auth"`, and the code took `qopList[0]`, put that token in the `qop=` parameter it emitted, and then hashed `H(method:uri)` — the `auth` formula — regardless. The client told the server it was applying entity-body integrity while applying none, and the response is wrong for the `qop` it declared, so every conforming server rejects it with a 401. `auth-int` also cannot be implemented here at all: the entity-body hash is part of HA2 and no version of this API receives the body. The response now requires `auth` in the list and uses it, and a challenge offering only `auth-int` is refused with a message that says why, rather than answered wrongly.
- **An unrecognised `algorithm` silently became MD5, and the `-sess` forms were computed with the wrong hash.** `resolveHashAlgo` matched `SHA-256` and `SHA-512-256` and defaulted everything else to `MD5`, so `algorithm=MD5-sess`, `SHA-256-sess` and `SCRAM-SHA-256` were all answered with a 32-hex **MD5** response under a header naming a different algorithm. The server rejects that, and the rejection is about an algorithm the caller never asked us to use. The `-sess` variants were broken twice over: their names do not match, and having failed to match they fell through the `hash` dispatch to its SHA-256 default — so `MD5-sess` was computed with SHA-256, and `SHA-256-sess` worked only by coincidence. `-sess` is now resolved to its base algorithm and implemented: HA1 becomes `H(H(user:realm:pass):nonce:cnonce)` per §3.4.4, so the credentials are bound to the session and cannot be replayed under a different nonce. An algorithm that is not MD5, SHA-256 or SHA-512-256 — plain or `-sess` — is an error naming the value received, and a `-sess` algorithm with no `qop` is refused because there is no cnonce to fold in.
- **A quote in a username, realm, nonce, uri or opaque broke out of its quoted-string and injected auth-params.** `formatDigestAuth` interpolated every value raw, so the username `admin", qop=auth-int, nc="ffffffff` produced a header carrying an attacker-chosen `qop` and a second `nc` — and because `realm` and `opaque` come from the **server**, a hostile or compromised origin could write into the client's own outgoing `Authorization` header. All five values are now escaped per RFC 7230 §3.2.6 (`\` and `"`), and `parseDigestChallenge` decodes those escapes on the way back in, so a header round-trips.
- **`parseDigestChallenge` could not read back a quoted-pair.** The value pattern was `"([^"]*)"`, which stopped at the first quote regardless of a preceding backslash. `realm="say \"hi\""` parsed as `say \`, and the remainder was re-scanned as if it were another parameter — so a realm containing a quote silently truncated the challenge and swallowed whatever followed it. The pattern now accepts `quoted-pair` and the value is unescaped, which is what makes the round-trip above exact.
- **`userhash=true` was parsed, typed, documented and then ignored.** `DigestChallenge.userhash` was public with the JSDoc "true if the server supports hashed username (RFC 7616 §3.4.4)", and a server offering it got a plain `username="admin"` back — the username it had explicitly asked to be hashed, sent in the clear — with HA1 built from the unhashed name, so the request failed as well. The new `computeUsernameStar()` returns `base64(H(username:realm))` using the challenge's own algorithm, the hashed name replaces `username` inside HA1, and the header emits `username*`. `formatDigestAuth` refuses to format a `userhash` challenge without it, and refuses a `username*` value for a challenge that did not ask for one, so neither mistake can be made silently.

- **`authLink` never put a token on the wire (high).** The link wrote the `authorization` header onto `op.request.headers` _and_ onto `op.config.headers`; neither was ever read on the way to `fetch`. The terminal link closed over the constructor-time `this.config` and discarded whatever `op.config` a link had replaced it with, and `buildHeaders` only ever consulted `config.headers` — so `op.request.headers` was written and then ignored. Every authenticated request went out unauthenticated, and all three `authLink` tests passed throughout, because each of them asserted only that a public API still answered. The terminal link now honours `op.config`, and `buildHeaders` merges `req.headers` last so request-level headers take precedence.
- **`errorLink` did not await its handler, so `null` recovered instead of re-throwing.** The handler is typed `Promise<GraphQLResponse> | null` and documented that `null` means "re-throw", but the result was used without `await`. An async handler resolving to `null` therefore arrived as a **truthy Promise** and was returned as the response: the error was swallowed, the caller received `null` for its `data`, and then died on `null.errors` — a `TypeError` naming neither the cause nor the operation, some way from the failure. The one test covering this used the synchronous form, which is the only form the bug does not affect.
- **A negative `retries` or `maxRetries` threw `undefined`.** Both loops are `for (attempt = 0; attempt <= max; attempt++)`, so a count of `-1` made the condition false on the first evaluation, the body never ran, `lastErr` was never assigned, and the method ended in `throw undefined` — a rejection carrying no value, where even `err.message` throws a `TypeError` inside the caller's own error handler. Both now validate on entry and raise a `RangeError` naming the value; `retryLink` rejects at construction.
- **`batch()` silently returned the wrong number of results.** The results were mapped over whatever the server sent, with no check against the requests. Two requests answered with one result resolved to a one-element array, and one request answered with three resolved to a three-element array — with `requests[i]` `undefined` for the extra entries, so an `errors` in one of them was attributed to no request at all. Positional alignment is the entire point of a batch, so a length mismatch is now an `EINVALIDRESPONSE` naming both counts.
- **`batch()` threw a raw `SyntaxError` on a non-JSON response.** Every other path routes a bad body through `parseGraphQLResponse`, which yields a typed `EPARSE` / `ENETWORK` `GraphQLClientError`; `batch()` called `response.json()` bare. A 502 HTML page from a proxy produced a `SyntaxError` with **no `code` at all**, so a caller switching on `err.code` saw `undefined` and had no way to tell a network problem from a bug in their own code. It now checks status and content-type first and wraps parse failures in `EPARSE`, exactly as `query()` does. `batch()` also skipped query validation entirely, making it the one way past the length, depth and injection limits the module applies everywhere else; each query is now validated before anything is sent.
- **Upload paths were resolved against the wrong root, so no file ever bound.** The documented examples — `path: "file"` and `path: "input.file"` — produced `{"variables": {"file": {}}, "file": null}`: the null landed at the top level of the `operations` object, where no variable lives, and the real variable kept its original value. A purely numeric segment fared no better: `files.0` against an existing array left it as `[{}, {}]` and wrote the nulls to a stray sibling `{"0": null, "1": null}`, so the positions the `map` pointed at held nothing. Paths are now rooted at `variables` automatically (both spellings are accepted, and the `map` always carries the rooted form the multipart spec requires) and a container whose next segment is an index is created as an array.
- **The query validator read string literals as if they were code.** Both the injection scan and the brace counter ran over the raw document, so a query the caller was entitled to send was rejected: `{ search(term: "javascript:void(0)") }`, `{ run(code: "eval(x)") }`, `{ page(html: "<div onerror=alert(1)>") }` and `{ css(v: "<!-- hi -->") }` were all refused as malicious, and `{ a(s: "}") b }` was refused as _unbalanced braces_. Structural checks now run over the document with its ordinary and block-string values (all three quote styles) and `#` comments blanked out, so a brace or a keyword inside a value is data rather than syntax. Every pattern is still rejected in exactly the same place outside a literal. A client refusing to transmit a well-formed query is a hard failure for the caller, and none of these was ever a client-side hazard in the first place — what a _server_ renders from a string it was sent is the server's responsibility to escape, which a scan of the request text cannot check anyway.
- **Every anonymous operation was handed to `onRequest` with `operationName: null`.** `extractOperationName` returns `string | null` and the guard read `!== undefined`, which `null` satisfies. So `{ anon }` produced a request object with `operationName: null` — visible to `onRequest` hooks, to links, in `loggingLink`'s payload, and on the resulting `GraphQLClientError`. The guard is `!== null`; an anonymous operation now sends no `operationName` at all, while an explicitly passed `""` is still treated as absent rather than silently replaced by the auto-extracted name.

- **`parseParams` split on every semicolon, including those inside a quoted value.** The parser was `paramStr.split(";")`, so a value containing one was shredded into extra parameters: `boundary="a;b"` yielded `boundary` = `"a` plus a stray `b"`, and `Content-Disposition: form-data; name="file"; filename="report; final.pdf"` lost the filename entirely. Semicolons are legal in filenames, and the multipart spec's own boundary example trips it. `parseParams` is also what `parseContentType`, `parseContentDisposition`, `parseCacheControl` and `parseServerTiming` read their parameters through, so all four inherited it. Splitting is now quote-aware and honours `quoted-pair` (RFC 7230 §3.2.6), and values are unescaped on the way out — `filename="a\"b.txt"` now yields `a"b.txt` rather than `a\"b.txt`.
- **Every formatter interpolated parameter values raw, so a quote broke out of its quoted-string.** `formatLinkHeader` emitted `title="a "q" b"` and an unknown parameter `x` with value `v"w"` emitted `x="v"w""`; `formatServerTiming` did the same to `desc=`, and `formatContentDisposition` to `name=` and `filename=`. A recipient reads the remainder as further parameters. All quoted-string values are now escaped per RFC 7230 §3.2.6, and each of these round-trips through its own parser.
- **`parseRange` accepted ranges that RFC 9110 §14.1.1 calls invalid, and produced `NaN` bounds.** `bytes=abc-def` came back as `{ start: NaN, end: NaN }` — `parseInt` returns `NaN` and nothing filtered it, so a caller doing arithmetic on the bounds got `NaN` rather than a rejection. `bytes=500-100` was accepted with `start > end`, and `bytes=` parsed as a valid, empty `RangeSpec`. Non-finite and negative bounds, inverted ranges, and an empty range list are now all rejected; one bad element in a list no longer discards the good ones, and the suffix form `bytes=-500` (and `bytes=-1`) still parses.
- **A malformed q-value was read as "not acceptable".** `quality = parseFloat(v) || 0` turns `NaN` into `0`, and `q=0` means the client will not take that type — so `Accept: text/html;q=abc` silently stopped matching `text/html`. Values outside the RFC 9110 §12.4.2 range were not bounded either: `q=1.5` and `q=-1` flowed out of the parser as out-of-range weights. A q that is not a number is now treated as absent (the default, `1`), and numeric values are clamped to `[0, 1]`.
- **`negotiateContentType` had five separate defects.** An absent or empty `Accept` returned `null`, where RFC 9110 §12.5.1 says no `Accept` field implies _any_ media type is acceptable — a client that simply did not care got no match. Matching was `available.includes(value)`, so a server listing `text/html; charset=utf-8` was never matched by a client asking for `text/html`, and media types were compared case-sensitively, which RFC 9110 §8.3.1 forbids. Finally `q=0` was not honoured: `Accept: text/html;q=0` returned `text/html`, and `text/html;q=0, */*;q=0.1` returned `text/html` via the wildcard. Negotiation is now resolved per available type, taking the quality of the **most specific** matching range as §12.5.1 requires, and skipping anything at `q=0`.
- **`getClientIP` returned whatever the header happened to contain.** No validation ran, so `X-Forwarded-For: garbage` returned the string `"garbage"`, and `x-real-ip: not-an-ip` likewise — into rate-limit keys, access logs and geo lookups. The de-facto `unknown` placeholder that nginx, HAProxy and several CDNs emit was returned as though it were an address, and masked real addresses later in the list. An empty `X-Forwarded-For` returned `""` rather than the `null` its signature promises. Addresses are now validated (dotted quad or IPv6), `unknown` and empty entries are skipped so the search walks outwards to a real one, RFC 7239 obfuscated identifiers are passed through as the RFC allows, and the return is always a usable address or `null`.

- **The retry interceptor treated a malformed `Retry-After` as a date in the past, skipping the back-off entirely (high).** `retryAfterMs` handed the raw header to `Date.parse`, which is lenient far past RFC 9110 §10.2.3: it reads `"1.5"`, `"-5"`, `"+5"` and `"0.5"` as perfectly good ancient dates. Each therefore resolved to a delay of ~0 ms, so a server sending a value kinetex could not understand produced an immediate re-send — the exact thundering herd the back-off exists to prevent, and the client-side mirror of the `Retry-After` defect already fixed in `client.ts`. A delta-seconds value is still read as seconds, and a well-formed HTTP-date in the past still means "retry now" (`0`); only the three formats RFC 9110 §5.6.7 defines are accepted, via the same `parseHTTPDate` the client uses.
- **`maxDelayMs` was not a maximum in the retry interceptor either.** The client-side cap was corrected earlier in this release; the interceptor carried its own copy of `computeDelay` with the original ordering, so the cap was applied to the exponential base and jitter was then added on top, uncapped. With `baseDelayMs: 1000`, `maxDelayMs: 1200` and `jitter: 1` the interceptor waited 2000 ms. The two implementations now behave identically, and the cap is re-applied after jitter.
- **`redactHeaders` on the logging interceptor did nothing at all (high).** The option is documented as "Header names whose values should be redacted in logs" and defaults to `authorization`, `cookie`, `set-cookie` and `proxy-authorization` — but the function that applied it was never called, never returned and never attached to anything, carrying a `void redactHeaders; // used externally` to silence the unused warning. No headers were emitted on any log entry, so a user who configured extra names, or read the default as protection they were getting, had neither the feature nor the protection. Every `LogEntry` now carries a `headers` field: the request headers, with the value of each configured name replaced by `**REDACTED**`. Matching is case-insensitive, so a config written `X-Api-Key` still redacts a header sent as `x-api-key`.
- **Body sizes were counted in UTF-16 code units, not bytes, everywhere the library reports a byte count.** `computeBodySize` returned `body.length` for a string, and the HAR recorder computed its response `bodySize` and `content.size` the same way. `"héllo"` reported 5 instead of 6, `"日本語"` 3 instead of 9, and `"😀"` 2 instead of 4 — every non-ASCII body under-reported in HAR archives and metric byte counters, worst at one quarter of its true size for astral characters. Both now measure UTF-8 bytes. `Uint8Array` and `ArrayBuffer` were already correct, `-1` for a body whose size cannot be determined is unchanged, and a size HAR cannot express stays `0` there.
- **`createRateLimitInterceptor` accepted a configuration with no valid token bucket.** `limit` and `windowMs` were never validated, and the refill interval is `windowMs / limit`: with `limit: 0` that is `Infinity`, which `setInterval` clamps to 1 ms — a busy-poll running for the life of the process, with `tokens` pinned at 0 and every waiter held indefinitely. A negative or non-finite `limit` or `windowMs`, or a negative `maxQueue`, now throws a `RangeError` naming the field and the offending value, at construction. `createInterceptorSuite` and `kinetex({ rateLimit })` inherit the check, so the failure is immediate and named rather than a hung queue.

- **`withBaseURL` produced a double slash for the most common `baseURL` spelling (high).** The join rule was "insert a slash unless the base already ends with one _or_ the path already starts with one" — which is wrong precisely when both are true. `withBaseURL("https://api.test/v1/")` applied to `"/users"` returned `https://api.test/v1//users`, and `baseURL: "https://api.test/"` is how most people write it. The extra slash reaches the server as a distinct, empty path segment, so a signature computed over the path, a route matcher, or a CDN cache key all see a different URL from the one the caller asked for. Both sides are now trimmed and exactly one slash is inserted, which is right in all four combinations and collapses runs of slashes.
- **A recovered error was never published to `emitter.on("error")` (high).** `runOnError` emitted the `error` event on the line after its loop, and the loop's recovery branch did a plain `return` — so an error that an on-error hook recovered from was the one kind the emitter never heard about. That is the wrong way round: a recovered error is swallowed, so the caller never sees it either, and the event was the only remaining notification of it. The event is now emitted on every path, and the recovery result is captured rather than returned from inside the loop.
- **`condition` was ignored by two of the twelve phases.** `runOnCancel` and `runOnConnection` looped over their hooks without calling `_shouldRun`, so `addOnCancel(fn, { condition })` ran the hook unconditionally — the option was accepted, documented on the shared `HookOptions`, and did nothing. `runOnConnection` was not even given a `HookContext` to evaluate a condition against; it now takes one, as a **required** parameter, because an optional one preserves the silent-no-op for every caller that omits it and that is a wrong answer rather than a compile error.
- **`safe` was ignored by five phases, in both directions.** The progress, cancel and connection phases each used a bare `try {} catch {}` that swallowed everything, so `safe: false` — the documented default, "critical hooks that must propagate errors" — never propagated, and `safe: true` was the only path that produced the log line the other seven phases write. Around hooks erred the other way: `safe: true` was ignored and a throwing around hook took the request down regardless. All five now share an isolator that rethrows unless `safe` is set, logs the hook id when it is, and — for an around hook that throws before calling `next` — still runs the dispatch, since there is no response to return and the pipeline cannot continue without one.
- **`HookEmitter.emit` was not re-entrancy safe.** The loop walked the live listener array and re-checked its length, so a listener that registered another listener had the new one called by the emit already in progress. The trailing write-back that drops `once` listeners rebuilt the list from the snapshot taken _before_ the emit, so a listener that called `off()` mid-emit had its removal undone. Emission now iterates a snapshot and removes `once` listeners by identity against the current list, so anything added or removed while an emit is in flight is left as the listener left it.
- **`createLoggingHooks` wrote `Set-Cookie` to the log in cleartext by default.** Its default `redactHeaders` was `["authorization", "cookie"]`, while `afterResponse` logs _response_ headers — so every cookie the server set was emitted verbatim on a hook whose only purpose is logging. The interceptors' own logging defaults already redact all four names; these now match. An explicit `redactHeaders` still replaces the default rather than adding to it.

- **`ConsoleTransport` threw on the first write unless `onWrite` was supplied (high).** `onWrite` is a required field of `ConsoleTransportOptions`, but the constructor's default parameter only supplied it when the _whole_ options object was omitted. `new ConsoleTransport({})` — which every caller assembling options at runtime reaches, and which the type's own optionality invites — left `this.onWrite` undefined and failed with `this.onWrite is not a function` on the first `write()`. The field is now optional and defaulted like every other one.
- **`new ConsoleTransport()` contradicted its own documented default.** The no-argument form took a default parameter object that hard-coded `pretty: false`, while any other call form resolved `pretty` against `NODE_ENV`. So `new ConsoleTransport()` emitted JSON and `new ConsoleTransport({ onWrite })` emitted pretty output in the same process — against a doc comment reading "Defaults to true in non-production". One resolution path now serves every call form.
- **Body sizes and truncation were measured in UTF-16 code units and labelled bytes (high).** `redactBody` reported `str.length` as the entry's `bodySize` and truncated on the same unit, writing `truncated N bytes` for a character count. `maxBodyLength` is documented in bytes, and the file already had a `bodySize()` helper that counts UTF-8 — used on the _suppressed_ path but not the logging one. An emoji body was reported at half its size and kept twice the configured budget; a CJK body, at a third. Both are now UTF-8, and truncation never splits a character. The reported `size` is the body **as received**, measured before decoding: two invalid UTF-8 bytes decode to two U+FFFD characters that re-encode to 6, and reporting 6 for a 2-byte body describes nothing the caller sent.
- **A filtered response leaked its active ID, permanently (high).** `logResponse` deleted its `activeIds` entry _after_ the filter's early return, so any response dropped by `statuses`, `methods`, `level`, `excludeURLs` or sampling left the record behind. The only cleanup is a size-triggered sweep inside `logRequest`, so a service logging with a narrow status filter accumulated one dead entry per request until it reached the 10000 cap — at which point eviction begins removing IDs of requests still in flight. The release now happens before the filter, as it already did for the unfiltered path.
- **A size-triggered flush left the batching timer armed.** `BatchingTransport.write` and `RemoteTransport.write` flush when the buffer reaches `maxBatch`, but that flush did not clear the pending interval. `write`'s `if (!this.timer)` guard therefore stayed false for the next entry, which got no timer of its own and waited out the remainder of the previous batch's interval — and a process that filled a batch and then went quiet held the interval for the whole `flushMs` against an empty buffer. Both flush paths now disarm first.
- **`redactURL` leaked query parameters on every relative URL (high).** Anything the `URL` constructor rejects fell into a `catch` that returned the input untouched, so `logRequest(id, "GET", "/users?token=abc", ...)` wrote the token in clear while the absolute spelling of the same request redacted it — and `HTTPLogger.child`'s own doc example logs a relative URL. Relative forms now get a textual pass over the query string, with percent-decoded names matched and the fragment preserved.
- **A structured rejection logged as `"[object Object]"` with no code.** `serializeError` handled `Error` instances and fell through to `String(err)` for everything else, so a rejected object — what a custom `fetch`, a GraphQL client or a worker handler throws — produced an entry whose message was literally `[object Object]`, with `code` dropped entirely. An error-shaped object now keeps its `name`, `message`, `code` and `stack`; anything else is stringified structurally, with circular references marked rather than thrown.

### Removed

- **`"HTTP/3"` as a reported `HTTPVersion` (breaking for type-level consumers only).** Some runtimes advertise `h3` in `Alt-Svc`, and detection mapped that to an `HTTP/3` response version — a value no transport here could produce, since none of them speak QUIC. `HTTP/3` has been dropped from the `HTTPVersion` union; `Alt-Svc: h3` is now reported as `HTTP/2` when `h2` is also advertised and ignored otherwise. There is nothing to implement against today: Node's QUIC API has not shipped in a stable release, Deno's `fetch` HTTP/3 support is still an open issue, and Bun's `node:quic` is listen-only.

### Documentation

- **The concurrency limiter was documented nowhere (high).** It is one of the six capabilities this release adds, and the changelog claimed a "Concurrency Limiting" section for it — but the README had no such section, no table-of-contents entry, and no `concurrencyLimit` line in the client-configuration block. A reader could not have discovered that the option existed, let alone that a permit is held across retries or that `maxQueue` is validated. The section now exists, with the config shape, the `ECONCURRENCY` versus `EABORT` distinction, the `maxQueue` contract, and the standalone `ConcurrencyLimiter`.
- **The configuration block still said `proxy` fails fast, which this release made false.** The note claimed "kinetex's built-in transports cannot route through it" and showed the option commented out with a SOCKS5 URL — while the HTTP(S) CONNECT proxy added below it works on Node, on both built-in transports. The block now shows an HTTP proxy as usable and keeps the SOCKS5 caveat, which is the part still true.
- **The Redirects section contradicted itself.** The bullet list said exhausting `maxRedirects` raises `ENETWORK` ("Too many redirects") and that a loop is refused with `ENETWORK` ("Redirect loop detected"), while the paragraph further down the same section said a redirect failure is a `RedirectError` with code `EREDIRECT`. The bullets were left behind when the codes changed; verified at runtime, both are now `RedirectError` / `EREDIRECT`.
- The README gained a "Where pooling actually happens" table. Only the HTTP/2 row is tuned by `sessionPool`; the `FetchTransport` rows (HTTP/1.1 on Node, and every non-Node runtime) are pooled by the _runtime's_ own `fetch`, and kinetex exposes no connection-limit or idle-timeout control over them. That distinction was previously undocumented and easy to assume away.
- `sessionPool` is documented as ignored when a custom `fetch` is configured or `httpVersion: "HTTP/1.1"`, since both select `FetchTransport` and bypass the pool.
- New sections: "Concurrency Limiting", "HTTP(S) Proxy", the OTel metrics subsection, and the Idempotency-Key subsection. The runtime-compatibility table now lists zstd, CONNECT proxy and the concurrency limiter in place of the removed HTTP/3 row, and the error-code table gained `ECONCURRENCY`.

### Tests

**`tests/headers.test.mts` 275 → 295.** The suite was already free of assertion-free and log-only tests; what it lacked was anywhere to assert the _shape_ of a header. Eight weak assertions were tightened (`toFlatObject` was `typeof === "string"`, `parseForwarded` used `Array.includes`, `/ip` and `/uuid` checked `includes(".")` and `includes("-")`), and one test was checking nothing it claimed: `GET /response-headers returns custom header with Location` asserted only `status === 200`, never the `Location` header it had just asked httpbin to send.

**The suite was also testing the wrong `parseContentType`.** Two functions share that name — the one in `headers.ts`, and a deliberately narrowed, DoS-guarded wrapper in `response.ts` that the package root re-exports. The suite imported it from `mod.ts`, so it exercised the wrapper and the `headers.ts` function was never tested at all, its `params` field included. Both contracts are now pinned, and the difference between them is stated in a test rather than left to be discovered.

**`tests/graphql.test.mts` 66 → 104.** The suite is built on live public APIs — `countries.trevorblades.com`, `rickandmortyapi.com`, `graphqlzero` — so most of it could only assert that _a response came back_. That is not nothing, but it is blind to everything on the request side, and that is exactly where the `authLink` defect lived: three tests named after the link, none of which could have noticed it never sent a header. A local recording server now sits at the top of the file, and the assertions that matter are about what was transmitted.

Beyond that: `retryLink catches network errors` was a bare `try {} catch { assert.ok(e instanceof Error) }` and would have passed on success; `upload with mock fetch` asserted `assert.notEqual(r, null)`, which any object passes; `introspect specific types` called `introspect(["Query"])` on a method that takes **no arguments**, so the "specific types" its name promised were never requested. The `uuid` / `ip` / `json` tests asserted truthiness and are now shape- and format-pinned, including that two `uuid` calls do not return the same value.

**`tests/digest.test.mts` 31 → 58.** The suite claimed to use known-good vectors ("Known-good test vectors from RFC 7616 Appendix A") and never asserted one: every hash test checked `typeof resp === "string"`, or a length, or that two values differed. Any hash of anything passed. The expected values are now pinned exactly, taken from an independent `node:crypto` reference rather than from the implementation's own output, and the RFC 2617 §3.5 and RFC 7616 §3.9.1 vectors are asserted for the first time.

Two gaps in coverage were more consequential than the weak assertions:

- **`createDigestAuthorizer` was untested.** It is the entry point `Kinetex`'s own `auth: { type: "digest" }` interceptor uses — the stateful one whose whole reason for existing is that `nc` must strictly increase — and not one of the 31 tests imported it. A full-codebase review pass — source correctness, then a documentation audit that checked every README section and inline JSDoc example against the implementation. ### Documentation

A second audit pass found documentation defects that the first round missed, because the docs-drift test only treated two diagnostic codes as drift. It now also fails on TS2339 ("property does not exist"), which is what caught most of these. All eleven are fixed:

- **Fluent builder documented as an unbroken chain.** The "Fluent Request Builder" sample chained `.send().json().text().bytes().blob().data().subscribe()` onto one expression. Every terminal method returns a promise, so only the first can be called; the sample now shows one terminal call per request.
- **`HookEmitter.clear()` does not exist** (it is `removeAllListeners()`), and the sample used `beforeRequest` with a `(req, ctx)` pair — the real event names are colon-separated (`before:request`) and `emit()` is async and takes a single event object. The full event-name list is now documented.
- **`Socks5Tunnel.send()` does not exist.** `createSocks5Tunnel` is a low-level primitive returning `{ conn, boundAddr, boundPort }` — a raw TCP socket, not an HTTP client. The sample invented a request API, omitted two of the function's three required arguments, and implied kinetex could route over it unaided. Rewritten to show the real shape and to state that reaching kinetex's pipeline means supplying your own fetch over the tunnel.
- **`withDownloadProgress()` destructured as `{ stream }`.** It returns `{ response, tracker }`; only the upload wrappers return a `stream`. `streamWithProgress()` was also shown as returning `{ stream }` when it is an async generator yielding `{ chunk, progress }`, and its options are `Omit<ProgressOptions, "onProgress">` (progress arrives per chunk), so the sample's `onProgress` callback could not compile.
- **`gql` used as a tagged template in five places.** It is a one-shot _function_ — `gql(url, query, variables?, headers?)` — and there is no template-tag form. Related: `client.query()` resolves to the response's `data` field directly, not to a `{ data, errors }` envelope; a non-empty `errors` array throws `GraphQLClientError`. The samples now say so, and `client.graphql()` is documented as returning a `GraphQLClient` rather than shadowing the imported `gql`.
- **AWS SigV4 chunked signing documented with a fabricated signature.** `initChunkedSigning(request, config)` returns `{ signedRequest, state }`; `signChunk(chunk, state)` returns `{ chunkHeader, newState }` and `signFinalChunk(state)` returns a string. The sample invented `sessionToken`/`dateTime`/`chunkIndex`/`previousSignature` parameters, and omitted that `newState` must be threaded into the next call.
- **`URLBuilder` sample called `.toString()` and then read `.href`/`.protocol`/`.searchParams` off the result**, which is a `string`. The builder is now kept in a variable and rendered separately.
- **`detectHTTPVersion()` presented as public API.** It is an internal, non-exported helper in `core.ts`; the compatibility note now says so and points at `KinetexResponse.httpVersion` instead.

- **`client.get("/users/1").json<User>()`** in the `Kinetex` class JSDoc: `get()` returns a `Promise`, so `.json()` cannot be chained onto it. The uppercase `GET()` builder is required. The same example passed a single object to `send()`, which takes `(url, method, options)`.

### Security

- **SSRF (critical):** redirect targets are now re-validated. `isSafeURL` only screened the _initial_ URL, so a public host returning `302 → http://169.254.169.254/…` reached the link-local/IMDS address with the whole private-range block list bypassed. Every hop now runs the same SSRF check, and `httpsOnly` is re-checked per hop so a redirect is no longer a trivial https→http downgrade.
- **Cross-origin credentials without a cookie jar:** `CROSS_ORIGIN_STRIP_HEADERS` was only applied by the manual redirect follower, which runs _only_ when a cookie jar is active. With the default path (`redirect: "follow"`) the Fetch spec drops only `authorization`/`cookie`/`proxy-authorization`, so a custom API-key header was forwarded verbatim to any redirect target. Requests carrying a known credential header — or a declared `apikey` auth (whose name is application-chosen and therefore unknown to the library) — are now followed hop-by-hop and stripped on origin change.
- **Cross-origin cookie leak:** the strip loop ran _after_ the jar-scoped `Cookie` header was rebuilt, deleting it again, so every cross-origin hop was sent without the cookies the jar had just scoped for the target. The order is corrected; same-origin hops are unaffected.
- **HAR (high):** HAR entries redacted credential _headers_ but stored the full `request.url`, every `queryString` value, the `Location` header and the entire response body verbatim — in a format whose stated rationale is that HAR logs are routinely exported and shared. URLs now have sensitive query parameters (and the fragment) masked, `Location` is redacted, body text is recorded only for JSON/XML/text content types and truncated to 8 KiB, and HTML bodies are never recorded.
- **Dedupe interceptor (critical):** `createDedupeInterceptor` keyed on `METHOD:url` with no auth fingerprint and handed the leader's response object to every waiter, so two callers with different `Authorization`/`Cookie` for the same URL received each other's data. The key now includes the same fingerprint the client's built-in dedup uses.
- **Cache/dedup credential coverage (high):** the auth fingerprint only hashed `authorization`, `cookie`, `x-api-key` and `x-auth-token`, while the redirect strip list treated ten more headers as credentials. A single shared `CREDENTIAL_HEADERS` list now backs the cache key, the dedup key and the cross-origin strip list, so a custom auth header can no longer silently collapse two users into one cache entry. Fingerprinting is also case-insensitive on header names.
- **SOCKS5:** the IMDS role name returned by the metadata service is now `encodeURIComponent`-escaped before being interpolated into the credentials URL path.

### Fixed

- **Crash / wrong error (critical):** the download-progress stream wrapper closed over the same `let` that was reassigned to the wrapper, so `cancel()` cancelled _itself_. `readRawBody`'s `reader.cancel()` (size limit exceeded, abort mid-download, read error) re-entered it, which threw `TypeError: Invalid state: ReadableStream is locked` from inside the cancel algorithm and left the inner promise unhandled — a process-level crash on Node. `maxResponseSize` + `onDownloadProgress` now yields the intended `SizeLimitError`.
- **Backpressure:** `withUploadProgress` and `withDownloadProgress` drained their entire source inside an `async start()`, enqueueing every chunk before the transport or consumer read a single byte — a large transfer was fully buffered in memory and the stream high-water mark bought nothing. Both are now pull-based (`start`/`pull`/`cancel`).
- **Type narrower than runtime (bodies):** the client has always JSON-encoded a plain-object/array body and set `content-type: application/json` when the caller supplied no content-type, but `SendOptions.body` and the `post`/`put`/`patch`/`withBody` parameters were typed `BodyInit`, so the documented, tested and working call `client.post("/posts", { title: "x" })` did not type-check. A new exported `RequestBody` type admits those values; `KinetexRequest.body` stays `BodyInit | null` because the encoding has already happened by then.
- **Silently empty body for `URLSearchParams`/`Blob` (high):** the raw Node HTTP/1.1 and HTTP/2 transports write only streams, byte arrays and strings; any other `BodyInit` fell through to `stream.end()`/`req.end()` with no payload, so `client.post(url, new URLSearchParams({ a: "1" }))` reached the server as an empty request on the default HTTP/2 path. Both writers now serialize the body types `fetch` would have encoded, and a `URLSearchParams` body without an explicit content-type gets `application/x-www-form-urlencoded` so servers can parse it.
- **`Cache-Control` quoted values truncated:** `parseCacheControl` split the header on every comma, including commas inside a quoted string, so `private="field1, field2"` parsed as a single field `field1` (RFC 7234 §5.2). Directives are now split on commas outside quotes.
- **Lost response in `onError` hooks:** the error-hook bridge in `attachHookRegistry` hardcoded `response: null` on both the `HookError` and the `HookContext`, even when the failure carried a response (`HTTPStatusError` holds the `KinetexResponse`). Every bridged `onError` hook therefore saw no response — `createLoggingHooks()` in particular recorded `status: null` for 4xx/5xx, silently losing the status code in structured logs. The response is now carried through, and is still `null` for genuinely response-less failures (network, timeout, abort).
- **Memory (listener/timer leaks):** `pagination`'s `sleep()` and `xhrFetch` attached `{ once: true }` abort listeners that only self-removed when they _fired_, accumulating one dead listener (and its closures) per completed operation on a shared signal. Both now detach on settle. `denoTcpConnector` created a `Promise.race` timeout per read and never cleared it — one leaked timer per chunk on a streaming tunnel; the timers are now cleared in a `finally`.
- **Hang:** `nodeTcpConnector` did not latch socket EOF, so any read issued after the peer closed parked forever with nothing to reject it. EOF is now latched and reported as `null`.
- **Method casing:** `send(url, "patch")` passed validation but put the literal string `"patch"` on the wire, because the normalized method was computed and then discarded. fetch() only normalizes `delete/get/head/options/post/put`, so lowercase PATCH/CONNECT reached servers verbatim and drew `405`. The normalized method is now sent.
- **Digest auth:** `nc` was hard-coded to `00000001` for every request, so any server enforcing RFC 7616 replay protection rejected the second authenticated request with 401. The new `createDigestAuthorizer()` keeps a per-nonce counter (reset when the server issues a new nonce) and is what the client's 401-retry interceptor uses; the stateless `createDigestAuthorization` is unchanged for one-shot callers.
- **Abort during the retry loop raised the wrong error class.** The retry path's pre-flight `signal.aborted` check and its back-off `sleep()` both built a bare `DOMException("Aborted")`. That is a real `Error`, but not a `KinetexError`: it carries no `code`, so `err.code === "EABORT"` and `err.isAbort` were both `false` here while every other abort path in the library (all of `core.ts`) raised `EABORT`. A caller following the documented contract therefore got a structurally different error depending on purely incidental timing — if the signal fired while the request was in flight it saw `AbortError`/`EABORT`, and if it fired during the back-off sleep it saw an error with neither. Both paths now raise the library's `AbortError` (which still sets `name === "AbortError"`, so name-based checks like `isAbortError()` are unaffected). This is the error the README's error-code table promises for `EABORT`.
- **`maxReconnects` was unenforceable (SSE).** The cap was checked against a counter that is reset on every _successful_ connect, which is correct for back-off but fatal for a limit: a server that accepted the connection and then closed the stream cleanly reset the counter each time, so the check could never be reached and the client reconnected forever. A `maxReconnects: 1` client reconnected 31 times in 400ms in a test. Both the error and clean-close paths now compare against the number of reconnects actually performed (`health.totalReconnects`), which is what the option documents. The clean-close path also records `health.reconnectAttempt` (the error path already did) and now honours an abort immediately after its back-off sleep, rather than waiting out the full delay to notice.
- **Retry with a non-replayable body:** retrying a `ReadableStream`/`Blob` body re-wrapped an already-consumed, locked stream and transmitted nothing. Retrying such a request now fails with a clear `EVALIDATION` error instead of silently sending an empty body.
- **Interceptor re-send loop:** a response interceptor that returned a modified request recursed through `_executeOnce` without any bound. Re-sends are now capped (`__interceptorResendDepth`, limit 5) and throw a descriptive error instead of looping forever.
- **OTel span leak:** the span was created before the dispatch `try`, so a throw between `startSpan()` and dispatch (e.g. auth fingerprinting when Web Crypto is unavailable) abandoned it — never exported, never reporting the error. The pre-dispatch section is now guarded and always ends the span.
- **SWR stuck key:** if `getCache()` rejected in the background revalidation's `finally`, the in-flight marker survived and that key could never revalidate again — every future hit served it stale forever. The cleanup can no longer be skipped.
- **Dedup stale timer:** a new dedup window for a key did not clear the previous entry's timeout, so the stale timer later deleted the _new_, still-in-flight entry out from under its waiters.
- **WebSocket double reconnect:** the send-error path both called `ws.close()` and scheduled a reconnect, and the `onclose` handler scheduled another, overwriting the handle without clearing it — a duplicate connection and double-counted attempts on every send failure. The pending timer is now cleared first, and the reconnect timer is no longer `unref()`'d (an awaited `open()`/`for await` consumer depends on it).
- **Cache housekeeping:** tag-index references were left behind for entries missing from storage, growing on every eviction; `304` is no longer in the default `cacheStatuses` (the client revalidates rather than storing one); control-character stripping in cache keys no longer recompiles a `RegExp` per call.
- **Cookies:** a `Domain=Example.COM` attribute was stored verbatim while every lookup compared against a lower-cased host, so the cookie was stored and never matched again — the attribute is now normalized. `domainMatch` tested the _request host_ for being a public suffix, which could never fire and reported `Domain=com` as matching every `.com` host; it now tests the cookie domain. The probabilistic 1%-per-access cookie sweep is gone (the periodic cleanup timer already covers it).
- **`getClientIP`:** now accepts `{ trustedHops }` and selects the entry written by the last trusted proxy instead of the client-supplied left-most value, and normalizes `for="…"` quoting, `[ipv6]:port` and `:port` suffixes. The trust caveat is documented on the API.
- **`destroy()`:** no longer calls `cache.clear()` — releasing a client must not purge data, and a user-supplied adapter (localStorage / Cloudflare KV / Redis) would have lost every persisted entry. Explicitly call `client.getCache().then(c => c.clear())` to empty it.
- **`BatchQueue`:** `maxBatch` must be a positive integer and `flushMs` a non-negative finite number (both now throw `RangeError`); `maxBatch: 0` previously spliced nothing and made `flush()` spin forever. `flush()` is additionally bounded.
- **`transformResponse`:** receives the real response object (status/headers/url) instead of the `{}` placeholder it was handed before.
- **`maxRequestSize`:** a circular or `BigInt`-containing body threw a raw `TypeError` from inside the size guard; it is now wrapped in a `KinetexError` naming the real cause.
- **Circuit breaker:** `execute()` no longer throws synchronously when the guarded function throws (it always returns a promise, so `.catch()` works); the half-open probe slot is released based on whether _this call_ acquired it, rather than on the state at settle time; `snapshot` no longer allocates an array per call.
- **WebSocket `worker` entry docs:** the module header claimed HTTP/2 was unavailable while the `kinetex()` example advertised it — the entry point always uses `FetchTransport` and defaults to HTTP/1.1, and now says so.

### Added

- `getClientIP(headers, { trustedHops })` — proxy-aware client-IP extraction.
- `createDigestAuthorizer()` — stateful Digest auth with a per-nonce request counter.
- `CREDENTIAL_HEADERS` (exported from `cache.ts`) — the single list of credential-bearing header names, re-exported for callers building their own cache/dedup keys.
- `maxRedirects` and `followRedirects` are now actually honoured. Both were documented on `KinetexConfig` and `SendOptions` and silently ignored; the manual redirect follower now enforces the per-request/client limit (`0` disables following and returns the 3xx as-is), and the documented default was corrected to the enforced one (20).
- `tests/regressions.test.mts` — 131 tests, one per finding, plus edge cases: the SSRF address matrix on redirect hops, cross-origin cookie matrices, `apikey`/custom-header handling with and without a cookie jar, unhandled-rejection and `SizeLimitError` assertions for the progress cancellation bug, per-identity dedup isolation and waiter abort, stream backpressure assertions, digest counter rollover and nonce rotation, SOCKS5 EOF-vs-hang timing, and redirect-limit behaviour.
- `NodeHTTP2Transport`'s `ca` option is now documented in the README (added in 1.2.0).

### Changed

See CONTRIBUTING.md → Release Process.
- Manually followed redirect chains now report `redirected: true`, matching what fetch() reports under `redirect: "follow"`.
- `accept-encoding` is only stripped by `FetchTransport` when it exactly matches the value kinetex injects; a caller who deliberately set `gzip, deflate, br` (or any superset such as `+ zstd`) now keeps it.
- HAR timing uses `performance.getEntriesByName()` and requires a recent entry, instead of scanning every resource-timing entry per recorded request and potentially attributing another request's timings.

## [1.2.0] - 2026-09-26

### Fixed

- **Security (SSRF):** `isSafeURL`'s IPv4 literal parser now implements full WHATWG shortcut-host semantics — the last dotted component absorbs the remainder of the address (`127.1` → `127.0.0.1`, `169.254.43253` → link-local/IMDS), and a single trailing dot (FQDN form, which URL parsers keep verbatim and fetch resolvers treat as the same host) is stripped before parsing. Together these close a bypass where trailing-dot shortcut hosts were previously treated as domain names and allowed through the private-range check. The dead conditional in the last-octet bounds check was removed.
- **Memory (listener leaks):** abort-signal listeners registered with `once: true` are now also removed when the operation settles — GraphQL execute/upload/batch, upload & download progress streams, XHR progress, the WebSocket external-signal close hook, and the timeout interceptor's merged-signal listener. Long-lived caller-provided signals no longer accumulate one closure per request (Node emits `MaxListenersExceededWarning` past 11).
- **HTTP/2 header validation:** the forbidden-control-character check in `NodeHTTP2Transport` is no longer gated behind strict mode — in non-strict mode (the default) an invalid header is now dropped with the `onDroppedHeader` callback / warning, matching `FetchTransport`, instead of the whole validation loop being skipped and the raw header crashing `session.request()` with `ERR_INVALID_HEADER_VALUE`. Strict mode still throws `EVALIDATION`.
- `NodeHTTP2Transport` (and `createTransport` session options) now accept a `ca` option so origins with self-signed or private-PKI certificates can be trusted without disabling TLS verification.

### Added

- Hardening test coverage: SSRF address-expansion matrix (IPv4-mapped/IPv4-compatible/NAT64/6to4 IPv6 forms, shortcut + trailing-dot IPv4 hosts), `randomBytes` CSPRNG contract, bearer/apikey header-injection guards (H3), `buildURL` manual-fallback safety check (M4), `maxRequestSize` body accounting for DataView/URLSearchParams/FormData/ReadableStream (H4), HAR recording + credential redaction, `CookieJar` `__Host-`/`__Secure-` retrieval-time defense (H5), and the GraphQL upload leaf-path pollution guard (H6).
- Additional hardening test coverage: client pre-flight guards (proxy fail-fast (M7), `httpsOnly` enforcement, unparseable-URL path exercising the manual-fallback safety check + `redactUserInfo` regex redaction, `maxRequestSize` accounting for ArrayBuffer/Blob/FormData bodies) and the timeout interceptor's merged external-signal lifecycle (abort propagation + listener cleanup on success/error).
- New local HTTP/2 test harness (`tests/h2-header-drop.test.mts`, Node-only): spins up a throwaway self-signed `http2.createSecureServer` (cert generated at test time into gitignored `tmp/`, skipped cleanly when openssl is unavailable) and covers the forbidden-header drop/callback/warn/strict paths plus per-request validation over the real HTTP/2 wire.
- Offline tests for the GraphQL external-signal lifecycle (query/upload/batch): assert the abort listener is added and removed on the caller's signal, that an external abort propagates and rejects, and that the no-CSPRNG `randomBytes` fallback throws — the httpbin-dependent graphql suite is skipped in CI, so these paths were previously unmeasured there.

## [1.1.0] - 2026-09-25

### Fixed

- **Security (SSRF):** URL safety checks now expand IPv4/IPv6 hosts to numeric form before range comparison, closing bypasses via IPv4-mapped IPv6 (`[::ffff:127.0.0.1]`, `[::ffff:169.254.169.254]`), hex/octal/decimal IPv4 literals (`0x7f000001`, `2130706433`, `0177.0.0.1`), and IPv6 aliases (`[::0:1]`). Covers loopback, RFC 1918, CGNAT, link-local (IMDS), IETF protocol, TEST-NET, benchmarking, multicast, and reserved ranges.
- **Security (redirects):** Credential-bearing headers (`Authorization`, `Cookie`, `Proxy-Authorization`, API-key headers) are now stripped when a redirect crosses origins, and auth re-application is suppressed on cross-origin hops — secrets are no longer forwarded to a different origin.
- **Security (HAR):** HAR entries redact credential-bearing request/response headers (`Authorization`, `Cookie`, API keys, tokens) before recording.
- **Security (URL):** the manual query-param fallback in `buildURL` now runs the SSRF safety check like every other path, and error messages redact `user:pass@` userinfo from URLs.
- **Security (auth):** `apikey` auth validates the custom header name (rejects CRLF/space injection) before applying it.
- **Security (prototype pollution):** untrusted JSON is sanitized (via the new `sanitizeParsedJSON`) at every remaining raw `JSON.parse` site — GraphQL single/batch/SSE responses, SSE `jsonSSE()` and `SSERouter.onJSON()`, WebSocket `message.json`, `deserializePaginationState`, and logging body redaction — so hostile `"__proto__": {...}` payload keys can never reach user code or downstream merges.
- **Security (GraphQL uploads):** upload variable paths are validated against prototype-pollution segments (`__proto__`, `constructor`, `prototype`); a crafted path like `__proto__.polluted` now throws `ValidationError` instead of writing through the prototype.
- **Security (logging redactor):** `redactObjectPath` never traverses or writes through pollution keys and uses own-property checks, so `bodyFields` selectors cannot be abused for prototype traversal.
- **Custom fetch honored everywhere:** a `fetch` option passed in config was silently ignored on Node.js when HTTP/2 was preferred (the default) — `NodeHTTP2Transport` has no fetch input. When a custom fetch is supplied it now always routes through `FetchTransport`, so the documented "custom fetch implementation" behavior (proxy agents, test doubles, request signing wrappers) works on every runtime.
- **Timeout:** `sendWithTimeout` races the transport against a deadline promise, so a transport that never resolves or ignores the abort signal can no longer hang the caller past `timeoutMs`.

### Changed

- `test:all` npm script now discovers all `tests/*.test.mts` files automatically (previously referenced three non-existent files and omitted several real test files).
- README: documented the `sanitizeParsedJSON` utility and kinetex's built-in prototype-pollution protection; corrected the `proxy` config / `.proxy()` fluent docs — the option fails fast with actionable guidance (undici `ProxyAgent` via `fetch`, or `createSocks5Tunnel()` for SOCKS5) instead of silently routing direct.
- README: documented previously-undocumented APIs — `WSClient` connection state/health (`state`, `connected`, `bufferedCount`, `metrics`, `waitForOpen`), rooms (`join`/`leave`/`rooms`), backpressure (`backpressure`, `drain`, `drainAndClose`, `drainBuffer`) and teardown (`close`/`destroy`); `SSEClient` lifecycle (`collect`, `close`, `destroy`, `streamHealth`). Corrected the Runtime Compatibility table: Brotli decompression is Node-only (`node:zlib`; other runtimes pass brotli bodies through), `WSClient` requires native `WebSocket` (Node 22+), URL pattern matching is kinetex's built-in implementation (all runtimes), and HTTP/2-via-fetch detection is best-effort (`Alt-Svc`/runtime hints). Fixed fluent-builder docs (`.withBody()`/`.params()` — `.body()`/`.query()` never existed) and `RetryContext` shape (`response`/`error` are non-optional, no `delayMs`).
